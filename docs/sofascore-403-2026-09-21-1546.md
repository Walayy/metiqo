# SofaScore : nouveau 403 à 15:46:40 le 21 septembre 2026

Diagnostic effectué sur les journaux Docker, le code réellement installé, les
tables PostgreSQL `ingestion_runs` et `collector_state`, puis par reproduction
avec Chromium sans réseau. Toutes les heures ci-dessous sont celles de Paris.
Aucune nouvelle requête de diagnostic n'a été envoyée à SofaScore.

## Conclusion et degré de certitude

Le nouveau refus est réel et survient pendant la découverte des journées, avant
l'ouverture des fiches de matchs. Le code exécuté n'effectue plus les anciens
appels JSON directs de compositions et de bans. Le cache, le contexte unique et
les pauses étaient actifs ; cela n'a pas suffi à éviter un nouveau 403.

L'utilisateur confirme que son navigateur habituel est lui aussi refusé. Une
restriction dépassant la seule session du worker, notamment liée à la connexion
ou à l'adresse IP de sortie, est donc l'hypothèse principale. Ce constat ne
prouve ni l'adresse utilisée par chaque navigateur, ni la règle interne du
serveur, ni que le dernier cycle est à lui seul responsable. Les anciens accès
peuvent encore contribuer à l'état de blocage côté source ; leur effet n'est pas
observable dans nos journaux.

Le volume exact de requêtes HTTP, l'URL refusée, son type de ressource, ses
en-têtes et son corps n'ont pas été conservés pour ce refus. Il serait donc
incorrect d'affirmer « trop de requêtes » comme cause certaine, de désigner un
fournisseur anti-bot précis, ou d'attribuer ce 403 à un endpoint particulier.

## Ce qui accède encore à SofaScore

- Le worker navigue vers des pages, lit leur DOM et les données SSR embarquées
  dans le HTML. Les anciens appels directs JSON de compositions et de bans sont
  absents du code installé, vérifié contre le fichier local avant correction.
- Le JavaScript de SofaScore peut toujours appeler ses propres services API,
  conformément à la demande de laisser charger le site normalement. Le worker
  surveille les statuts de ces réponses, sans lire leurs corps JSON.
- Les portraits déjà chargés peuvent être comparés au catalogue Riot local.
  Cela n'ajoute pas de requête API JSON.
- Le téléchargeur de logos possède encore une voie HTTP vers des images
  `img.sofascore.com`, distincte des API JSON. Le catalogue n'a pas tourné dans
  cette fenêtre ; aucune publication de nouvelle fiche n'a eu lieu. Rien ne
  l'implique dans ce cycle. L'import Oracle concurrent utilise une autre source.

**Huit pages lues ne signifient pas huit requêtes HTTP.** Une navigation peut
charger le document, des scripts, des images et plusieurs réponses de données.
Le budget applicatif compte les accès explicites, pas l'intégralité des requêtes
naturelles de Chromium. Aucun total HTTP fiable ne peut être reconstitué ici.

## Différences avec une navigation manuelle

Un seul processus navigateur principal était actif, avec le profil
`/data/browser/sofascore`. Ce profil était nouvellement créé lors de cette
relance : la persistance n'importe pas les cookies de l'ancien contexte ni ceux
du navigateur personnel.

Le binaire observé est **Chromium Headless Shell dans Linux/Docker**, lancé
sans canal Chrome, et non le Chrome Windows habituel de l'utilisateur.
Playwright documente ce choix par défaut et Chrome explique que le shell est
une implémentation distincte du navigateur complet. Cela établit une différence
d'environnement, pas la preuve qu'elle a déclenché le refus.
Sources : [Playwright — Browsers](https://playwright.dev/docs/browsers),
[Chrome — Headless Shell](https://developer.chrome.com/docs/automation-and-testing/headless-chrome-shell).

Chaque journée utilise `goto`, puis retourne à `about:blank` après lecture. Cela
arrête les actualisations de fond pendant la pause, mais recharge le document et
réinitialise l'application à la navigation suivante. Ce parcours diffère d'un
utilisateur qui reste dans l'application et change la date sans rechargement
complet. Il peut augmenter les requêtes de démarrage ; leur volume effectif et
leur rôle dans le blocage ne sont pas mesurés.

Les protections anti-bot peuvent combiner propriétés du navigateur, session et
comportement des requêtes. Le fait que le JavaScript du site émette les appels
n'empêche pas leur prise en compte. La documentation
[Cloudflare — Bot scores](https://developers.cloudflare.com/bots/concepts/bot-score/)
illustre ces mécanismes généraux ; elle **n'identifie pas** le fournisseur ou
la règle utilisés par SofaScore pour ce refus.

## Défaut local reproduit : perte du journal et du délai

La base affichait toujours le refus de **13:22:54** et son ancienne URL de match,
alors que `ingestion_runs` contenait le nouvel échec de 15:46:40. Cette ancienne
URL ne désigne donc pas la ressource refusée lors du dernier cycle.

Dans `_observe_response`, le code posait une erreur générique, puis fermait les
pages avant d'enregistrer le refus dans la politique persistante. Les appels
synchrones Patchright peuvent rendre la main à la navigation interrompue : le
cycle se termine et nettoie `_POLICY` avant que le callback reprenne. L'URL,
`Retry-After` et le délai progressif peuvent ainsi être perdus. Le scheduler ne
reçoit alors que `retryAt=0` et utilise son attente de repli.

Le comportement a été reproduit avec le binaire réellement installé, une
réponse 403 synthétique et Docker `--network none` : fermeture commencée,
erreur reçue par le cycle, nettoyage terminé, puis retour du callback sans
enregistrement du refus. Le script de diagnostic local est conservé sous
`.cache/sofascore-refusal-repro.py`, hors versionnement.

La correction enregistre et journalise désormais le refus **avant** l'appel
navigateur susceptible de rendre la main. La coupure réseau reste dans un
`finally`. La même reproduction avec le code corrigé conserve le refus et
transmet son délai avant le nettoyage. Deux régressions unitaires couvrent
403/document et 429/XHR.

Ce défaut explique les preuves manquantes et une reprise trop précoce par
rapport à la politique prévue. **Il n'explique pas le premier 403 de ce cycle** :
il intervient après réception du refus. La correction est locale et n'a pas été
déployée dans le worker arrêté.

l'aveugle ne permettrait pas d'obtenir la certitude demandée.
